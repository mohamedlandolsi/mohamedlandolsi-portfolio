## The problem

I needed clients for remote GTM automation work, and I wanted the search itself to prove I can do the work. Most outbound tools solve volume. My problem was the opposite: with free tiers only and a reputation to protect, every account, every contact and every sentence had to be right before it reached a person.

## What I built

A set of n8n workflows that started on one shared Google Sheet, so I could inspect and correct anything between steps. Clay now does the enrichment it is best at, and drafts and my decisions live in Postgres behind a private review console.

<Diagram name="gtm-engine-overview" alt="Three workflows in sequence. The engine discovers, filters, scores and enriches accounts, then queues them for contact lookup. The contact finder reads founders from YC company pages, with a gated search as fallback. The engine drafts messages, a validator checks them, and the digest pings Discord so I review each draft in the console. Google Sheets holds accounts, contacts and the Clay hand-offs; Neon Postgres holds config, drafts and review decisions." />

1. **Discover and filter.** Companies come from Y Combinator's public directory, Hacker News hiring threads and a seed list. Plain rules run before any AI call: domain, team size, industry, keywords, timezone and seen-before.
2. **Score and enrich.** Every account gets an explainable 0 to 100 score with its breakdown. A single website fetch detects the CRM and tooling the company actually uses. Accounts that score high enough go to Clay for structured research and, for the best ones, a recent trigger.
3. **Find the right person.** Founders are read from the company's YC page and accepted only if that page lists the same website. Companies outside YC go to a search with company and location gates. Clay then looks for a verified work email for one founder per qualified account.
4. **Draft, check, review.** A fallback chain of three Groq models and Gemini writes a LinkedIn note, a longer message and three follow-ups from facts only. A rule-based validator rejects bad drafts and asks for one repair. Discord pings me with a link, and I approve, edit or reject each draft in the console. Nothing is sent by the system.

### Review moved off the sheet

Reviewing drafts in a spreadsheet became the bottleneck, and I could not risk breaking a working engine to fix it. So I did not rewrite it. A new sync workflow mirrors the sheet into Neon Postgres <Metric claim="G26" inline /> and pushes my decisions back. Then the two tables that matter most for review moved over one at a time: the engine now reads its config from Postgres and writes new drafts straight there, each step behind a switch I can flip back.

The approval rules live in one Postgres function, not in the UI. A draft moves between pending, edited, approved, rejected, superseded and sent, and the database refuses every other transition: editing an approved draft sends it back for approval, and only an approved draft can be marked sent. Every action writes an audit row with the values before and after. Each table names who owns which field, and a console change carries a version stamp, so a change made while a sync runs goes out on the next run instead of being marked done by mistake ([ADR-S10-3](/decisions#ADR-S10-3)).

The console is a small Next.js app on Vercel's free plan, behind a single-owner password, and it works on my phone. Before the cutover the schema passed <Metric claim="G22" inline />. In production, <Metric claim="G21" inline />.

**A reason to write now.** The latest addition gives each hot account one recent, sourced trigger: a relevant job opening first, then a funding round, then news ([ADR-S11-3](/decisions#ADR-S11-3)). It travels from Clay through the sheet and Postgres into the drafting prompt and the console, and the validator accepts it as a fact a draft may quote. The first run limited the job search to GTM titles and found a trigger for <Metric claim="G24" inline />. Funding did no better: <Metric claim="G25" inline />. Provider coverage for small startups was the limit, not the build, so I widened the job search to sales roles and then any role while keeping the order strict. The final run covers <Metric claim="G23" inline />.

Two details mattered more than the providers. The news provider's date filter applies to when it first saw an article, not when the article was published, so the formula checks the article date itself. And the drafting validator rejects any currency sign, so a funding amount would have pushed every draft to the template: the import rewrites amounts as a number and a currency code, and the validator stays as strict as it was ([ADR-S11-7](/decisions#ADR-S11-7)).

### HubSpot as the system of action

Drafts and my decisions lived in Postgres, but there was no CRM to work the deals in. Accounts I approve now sync into HubSpot Free, and only those: a CRM should hold the pipeline I chose to work, not the raw prospect list ([ADR-090](/decisions#ADR-090)). HubSpot switched off new private apps the day I built this, so the sync authenticates with its new Service Keys ([ADR-091](/decisions#ADR-091)).

**An outbox in Postgres.** Neon views compute exactly what HubSpot is missing, already shaped as API requests and in order: companies, then contacts, then deals. n8n only carries each request and hands the answer to a Postgres function that records it. The sync has no Code nodes, its SQL passes <Metric claim="G30" inline />, and it runs <Metric claim="G31" inline /> while n8n runs ([ADR-093](/decisions#ADR-093)).

**Find or create, with adoption.** Every record is looked up in a link table first, then searched in HubSpot by its natural key: domain, verified email, deal name. A record found that way is adopted, not created again ([ADR-094](/decisions#ADR-094)). The first full run created <Metric claim="G27" inline />, and the run right after it wrote <Metric claim="G28" inline />. To stand in for a crash, I deleted one company link in Postgres and ran it again: the sync adopted the existing company under the same ID, and HubSpot held <Metric claim="G29" inline />.

<Screenshot project="personal-gtm-engine" id="hubspot-deals" />

**Ownership split and stage pull.** The engine owns the company and contact fields it sends, and HubSpot owns the deal once it exists ([ADR-095](/decisions#ADR-095)). When someone replies, I move their deal to Replied in HubSpot, and the sync pulls the stage back into the console ([ADR-099](/decisions#ADR-099)). Companies, contacts and deals sync live. Notes, follow-up tasks and the reply pull are built, awaiting first live send: the offline checks cover them, but no message has gone out yet.

**Claude as the operator layer.** Claude's HubSpot connector reviews the pipeline, audits data quality and moves a deal stage when I ask. It is never the sync: n8n stays the only writer of records, so every write is scheduled and logged ([ADR-101](/decisions#ADR-101)).

## What broke, and what I changed

**The search found strangers.** A people search for a company called Twenty returned people who worked somewhere else, because a company name alone is ambiguous. It happened at <Metric claim="G15" inline />. I replaced name matching with a lookup that is verified by website domain. On the next run, <Metric claim="G14" inline /> lookups resolved from YC pages, at no search cost.

**The validator was too strict.** In one run, <Metric claim="G13" inline />. Most rejections were word counts a few words short, not bad content. I relaxed the length rules, kept the factual checks, and added plain-language repair hints. In the latest run, <Metric claim="G7" inline />.

**The model pitched companies their own product.** With only a homepage description to go on, it treated what a company sells as a problem the company has. I added a deterministic product-term check that runs before and after the model: words the company repeats about itself may appear only in the opening observation.

**The EU portal rejected every contact.** The first HubSpot test created a company, then failed on its contact. The portal is on HubSpot's EU data center with GDPR features on, so it requires a legal basis on every contact. The fix was one view change: the outbox now sends the legitimate interest basis with each contact, from config ([ADR-102](/decisions#ADR-102)). The next run created the contact and its deal with nothing failed.

**Errors said only "Bad request".** That failure first reached the log as n8n's generic message, not the reason. The error step now stores HubSpot's own message, so the event log names the missing or wrong field. With a deliberately broken config, the run still completes, and every failed row names the bad property.
